## One working day for a useful code review

Run a four-week pilot for the 25-engineer team. Give the whole team one hour of protected time for a team meal or a shared break if it reaches the review target and passes the quality check. Let engineers choose which reward they’d value before launch.

### Before launch

Give five engineers 30 minutes of protected time to walk through recent slow reviews. Include people who regularly wait for reviews and people who receive a lot of requests. Fix the biggest bottleneck before starting. If requests sit because ownership is unclear, for example, assign one available reviewer through the existing repo workflow, name a backup, and protect time for reviews in the workday. Tell the team what changed because of their feedback.

### What counts

**A pull request earns one credit when a human reviewer submits a substantive approval or changes request within eight working hours of the PR becoming ready for review.** Use one published team calendar, with nights, weekends, and team holidays excluded. The clock starts when the PR is ready, even if nobody has been assigned yet.

Use existing PR and review events. An approval qualifies if the reviewer checked the scope and relevant tests or risks. A changes request qualifies if it gives the author a concrete next step. A bot response, emoji, or “looking now” leaves the clock running. A second review, reassignment, or reopening the same PR earns no extra credit. A withdrawn review that leaves no qualifying response by the deadline loses its credit. Substantive reviews done through the existing workflow still count. A chat reply counts once the reviewer records the decision on the PR.

Before launch, apply the rule to a duplicate review, a withdrawn approval, a chat-only response, and an unassigned PR. Agree on the expected result for each.

### Target and feedback

Recalculate the previous four weeks using the same rule. The denominator is every PR whose eight-hour deadline falls in the reporting period, including PRs still waiting at the deadline. The current 2.6-day median gives context. Use the measured one-day share to set the pilot target at **10 percentage points above baseline**. If 35% met the deadline before launch, the pilot target is 45% across the four weeks.

After a qualifying review, privately confirm which PR counted and when it was answered. Give each engineer a private goal based on their own review volume. A reviewer who typically gets five requests can aim to answer one more on time per five requests, up to five. Someone with fewer requests can carry that goal across weeks. A missed week simply leaves the next request as the next opportunity.

Post the team’s weekly count, percentage, and target in the channel it already uses for engineering updates. Managers see team totals. Use individual records only for a specific coaching or correction need.

### Quality and failure modes

The engineering lead samples five credited reviews each week, or all of them if there are fewer. Check whether the response was proportionate to the change and gave the author a sound decision or a concrete next step. **Two inadequate reviews in a sample, or one approval that bypasses a required check, pauses reward eligibility.** The lead explains the issue in aggregate, fixes the cause with the team, and resumes eligibility after a passing sample. Use existing PR records and keep reporting and sampling under an hour a week.

Watch for rushed approvals, draft status used to delay the clock, and easy PRs getting picked while harder ones age. Check the oldest waiting PRs alongside the quality sample. If requests pile up on a few engineers or reviews start spilling outside working hours, rebalance assignments and protect review time.

### Ending

By week four, make reviewer assignment with backup coverage and an oldest-first review queue the defaults in the tools engineers already use. End the reward after week four and recognize specific examples of reviews that helped authors move forward.

For four more weeks, track the same one-day share and sample review quality. Compare with the four-week baseline and, if a comparable team already has the same data, with that team over the same period. Keep the defaults if the improvement holds and quality stays acceptable. If it fades, use the oldest waiting PRs to identify what still blocks reviews and change the workflow there.
