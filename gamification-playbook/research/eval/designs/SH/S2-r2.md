## One working day for a first code review

Give every ready pull request a substantive first review within one working day. The current median is 2.6 days. Use a short team incentive to establish the habit, then keep the review rotation and protected time in place.

### Fix the review queue first

In week 1, ask five engineers who regularly write or review PRs where reviews stall. Use recent PRs to check what they report. Give the rotating primary reviewer a protected daily review block and name a backup who covers meetings, leave and spikes. Put the oldest ready PR first in the existing queue and use the team’s existing channel to flag cases nearing the deadline. Give engineers paid time to try the workflow and share what changed in response to their feedback. Start the reward once the rotation has enough capacity to clear the queue on a normal day.

### Reward a completed first review

**Team rule:** A ready PR earns one credit when another engineer submits a substantive approval or a review with specific, actionable feedback within eight hours on the team’s agreed working calendar.

Use existing PR timestamps and review records. Start the clock when the PR first becomes ready for review. Hours outside the team’s schedule, weekends and holidays do not count. The first qualifying review closes the clock. Assignment changes, draft toggles, duplicate reviews and reopening the same PR leave the original clock and credit intact. Acknowledgments, emoji and bot reviews earn zero credit. A PR merged without a qualifying review counts as a miss. Exclude only PRs genuinely withdrawn before the deadline, with withdrawals checked in the weekly sample.

The primary measure is **the percentage of eligible PRs that get a qualifying first review within one working day**. Measure it by the week the PR became ready and include unanswered PRs once their deadline passes. Reconstruct the previous four weeks from PR history to establish the baseline for this measure.

### Make progress visible

Use the existing PR notification to give reviewers a private confirmation when their review counts. Their personal goal is to answer their next assigned PR within the window. A missed review or a week away carries no penalty into the next case.

Post the team’s weekly percentage and PR count in its usual channel. Managers get the same team view. Individual counts stay private and are excluded from performance reviews. If at least 70% of eligible PRs receive a timely review over the four reward weeks, the team earns one company-paid lunch during working hours. Let the team choose an equivalent shared reward before launch.

### Run it for six weeks, then check again

Spend weeks 1–2 on queue fixes, protected time and feedback. Use weeks 3–6 for the reward. If the team already has two independent review rotations, start the second rotation’s four-week reward two weeks later. Both get the workflow fixes and feedback from week 1. If everyone shares one queue, use one start date and treat the trend as evidence about the combined programme.

Before the reward ends, make the ready queue and reviewer rotation the default in the PR workflow. End the reward on schedule. Four weeks later, use the same timely-review percentage to decide what to do. **Keep** the workflow at 80% or above. **Change** it if the result is below 80% but above baseline, using late cases to identify the bottleneck. **Drop** the incentive design if the result returns to baseline or worse, and keep any queue fixes engineers found useful.

### Catch failure early

The engineering lead spends up to 45 minutes a week checking five PRs, including quick approvals and any disputed counts. Before launch, test the rule on a duplicate, a draft toggle, an unreviewed merge and a withdrawn PR. If two of five sampled reviews are perfunctory, or a single sampled approval misses a material defect that was visible in the diff or checks, the lead pauses rewards and explains the correction to the team. The rotation owner fixes wrong counts raised privately.

Use oldest-first ordering and backup coverage to keep hard PRs from being passed over. If protected blocks keep overflowing, the lead adjusts coverage or workload. The one-day clock measures team service, so nobody needs to review after hours to earn the reward.
