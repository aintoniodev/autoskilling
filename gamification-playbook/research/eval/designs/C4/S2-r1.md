# One-day code reviews: an eight-week pilot

**The promise:** Get a useful first review within one working day. That means an approval or clear changes to make, not a promise to merge. No points, rankings, or individual prizes.

### Make reviews easier before offering a reward

Before launch, meet with five engineers who regularly author or review PRs. Give them 30 minutes of protected work time to walk through recent slow reviews. Fix the biggest bottleneck they identify and post what changed: “You reported it; we fixed it.” Start with a rotating primary reviewer and backup for each existing review group, a protected 30-minute daily review block, and an oldest-first queue in the tool engineers already use. The engineering lead cuts other commitments if the rotation cannot cover demand in normal hours. Don’t start prizes while reviews still depend on overtime.

### Reward a useful first review, once per PR

**The rule engineers see:** “Your group gets credit when the first real review of a ready PR is posted within one working day: approve it after checking the diff, or request changes with a specific next step.”

Use existing PR events: ready-for-review and submitted review. A non-draft PR starts the clock when opened; a draft starts it when first marked ready. One working day is eight hours on the team’s published working calendar, excluding nights, weekends, and team holidays. Individual leave is covered by the backup, not by stopping the clock. Count only human, non-author reviews. Chat acknowledgments, bot approvals, and “looking now” don’t count. A review posted through the old workflow still counts if it meets the same rule.

Attribute each PR to its owning review group when the clock starts. Reassignment, duplicate submissions, and draft/reopen toggles don’t restart the clock or create a second credit. If a review is formally dismissed before the deadline, use the next qualifying review, if any. Exclude bots and genuinely withdrawn work closed before the deadline; log exclusions and spot-check them for abuse. Dry-run these cases against real PR history before launch.

The score is **the share of eligible PRs whose deadline fell in the window that received a qualifying review on time**. Unanswered overdue PRs count as misses. Recalculate the previous four weeks using this definition: the current 2.6-day median is useful context, not the baseline for this percentage.

### Feedback and reward

After each qualifying review, send the reviewer a private confirmation in the existing tool: “PR #142: first review posted in 5 working hours.” The reviewer’s private goal is to cover the PRs due on their own rotation shifts, so the target scales with workload. No streaks or make-up quota after an absence. Post the team’s weekly on-time rate, with numerator and denominator, in its usual engineering channel. Managers see team totals only, with no individual drill-down, and the data stays out of performance reviews.

Each review group earns **one paid hour for self-directed learning**, scheduled in normal work hours, if it reaches **85% on time** across its four-week reward window and clears the quality gate. Everyone in the qualifying group gets it, regardless of personal volume. The groups do not compete.

### Timing, quality, and the decision

- **Weeks 1–2:** Everyone gets the workflow fixes and feedback; no prizes. **Weeks 3–6:** One review group, chosen by coin flip, is reward-eligible. **Weeks 5–8:** The other gets the same four-week window. Compare the groups in weeks 3–4 and each against its own feedback-only period. Treat the difference as directional, not proof.
- **Quality gate:** Each week, a designated senior engineer samples five credited reviews per reward-eligible group, or all if fewer. Check for rubber-stamp approvals and vague change requests. Two failures in a group’s sample pause its reward. The engineering lead decides when it can resume; the pilot owner corrects disputed counts from the PR record and replies privately. Budget 55 minutes a week for sampling, corrections, and the automated score check.
- **After week 8:** End prizes as announced. Keep the oldest-first queue as the default and leave the protected review blocks on the calendar. Four prize-free weeks later, use the same on-time rate: **85% or higher**, keep the workflow without prizes; **below 85% but above the feedback-only period**, fix the remaining bottleneck and retest without prizes; **at or below the feedback-only rate**, drop the incentive and stop its reporting. Keep any workflow fixes engineers find useful.

**Watch for easy PRs getting picked first, hard reviews getting rubber-stamped, and review work spilling into evenings.** Route complex PRs to a named reviewer early, keep late PRs visible in the queue, and adjust staffing rather than asking people to work faster or approve sooner.
