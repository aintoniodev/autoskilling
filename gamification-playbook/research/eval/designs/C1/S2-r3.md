## One-working-day code reviews

**Fix the review queue first.** Give each area a rotating primary reviewer and a backup, with protected review time each workday. When a pull request becomes ready, assign it to an available reviewer and put it in the team’s existing review queue, oldest first. Route around planned leave and flag unclaimed work halfway to the deadline. Before rewards start, check a sample of slow reviews and fix the biggest recurring blocker. Tell the team what changed, for example, “You flagged that reviews sat with people on leave. The queue now assigns their backup.”

**Reward a substantive first review.** A pull request earns credit once when a reviewer approves it after checking the change or requests changes with specific, actionable feedback, all within one working day. Acknowledgments, emoji, automated checks, and assignment changes earn no credit. An approval counts without a written comment if the review was substantive. The team earns a company-paid lunch, with an equivalent meal allowance for remote staff, if at least 80% of eligible pull requests meet the deadline across the final two weeks. Each person can miss a review and contribute on the next one.

**Measure from ready to reviewed.** Start the clock when a pull request first becomes ready for review, or at opening if it opens ready. Use eight hours on the team’s published working calendar, excluding evenings, weekends, and team holidays. Reassignment and pushing new commits leave the original deadline in place. Include all human-authored product pull requests that reach the deadline or receive a qualifying review earlier. Pull requests still waiting at the deadline count as misses. Exclude drafts that never become ready and track withdrawals before the deadline separately so closing and reopening work cannot quietly improve the score. Recalculate the prior four weeks using the same rules to establish a comparable baseline alongside the reported 2.6-day median.

**Show people what helps them act.** After a qualifying review, privately confirm which pull request counted and how long it took. Give each reviewer a private goal based on their assigned volume. For example, someone covering five reviews aims to answer four on time. Put the team’s on-time percentage, numerator and denominator, and open reviews nearing their deadline in the channel or queue engineers already use. Managers see team totals. Individual results are available to the reviewer and used in a specific coaching or correction conversation when needed.

**Run it for six weeks, then end the reward.** Use week one to check the baseline and fix routing or capacity. Run the incentive in weeks two through six and award the lunch once, based on weeks five and six. Before it ends, make automatic assignment, backup coverage, and oldest-first ordering the defaults in the existing tool. Keep those defaults and track the same measures for four more weeks. If timeliness falls, use the overdue cases to identify whether coverage, workload, or routing needs to change.

**Watch for shortcuts and displaced work.** Each week, the programme owner samples five credited reviews for rubber-stamping or vague change requests, checks withdrawals and overdue cases, and looks at time to merge and whether the same reviewers repeatedly absorb overflow. Correct any sampled credit that fails the rule. If first reviews get faster while merges slow down, inspect the handoff after the first response. If overflow repeatedly lands on the same people, rebalance the rotation. Automate the counts and confirmations so the owner can do the weekly checks and post the update in under an hour.
