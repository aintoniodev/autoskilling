## One working day for a first review

Give engineers a reliable review queue and protected time to work through it. Run a short trial with one shared reward. The team’s target is **80% of eligible pull requests receiving a substantive first review within one working day**. The current median is 2.6 days. Use recent pull requests to establish the baseline for the 80% measure.

### Fix the queue first

Ask five engineers who regularly author or review PRs what keeps reviews waiting. Use two weeks to address the biggest blockers. Start with a named backup for each code area, a protected 20-minute review slot each working day, and an oldest-first view of pending reviews in the tool engineers already use. Tell the team what changed in response to their feedback. If the queue still routinely exceeds available review time, fix coverage before starting the reward.

### What counts and what people see

**One PR earns one credit when another engineer submits a substantive review within eight team working hours of the PR being ready and review requested.** Agree on the team’s working hours and holiday calendar before launch. An approval after inspecting the change, a request for changes, or a submitted review with a specific technical question counts. Acknowledgments, emoji, and bot comments earn no credit. The clock continues through reassignment, and the backup covers absences.

Use existing PR and review events. Calculate the weekly rate from PRs whose deadlines fell that week, including those still waiting. Exclude drafts, bot-authored PRs, and PRs genuinely withdrawn before the deadline. A reopened or replacement PR for the same change keeps the original clock. Test the rule on a duplicate request, a withdrawn approval, an offline review, and a PR reassigned during an absence. An offline review counts once its substance is recorded on the PR.

Use the existing PR notification to give the reviewer prompt, private confirmation when a review provisionally counts. Their personal goal is to answer the next request they own within one working day. After an absence, they pick up the next request and the backup handles coverage. Post only the team’s weekly rate and PR count in its usual channel. Managers get that same view. Programme data stays out of performance reviews.

### Reward, timing, and ending

The reward is **one paid hour per engineer to use as they choose**, scheduled with coverage. The team earns it once by hitting 80% across the reward window and passing the quality check. Engineers on leave remain eligible.

Give everyone the queue fixes and feedback for two weeks first. Then run a four-week reward window. If the team already has two review groups with separate queues, start their four-week windows two weeks apart and apply the same milestone to each group. Compare the early group with the group still waiting during that overlap. If there’s one shared queue, run one trial and treat any improvement as the combined effect of the workflow and reward.

At the end of each window, award any earned time and close the reward. Keep the oldest-first queue and backup routing as defaults. Four weeks after the last window closes, use the same on-time review rate over those four weeks to decide what stays. **At 80% or above**, keep the workflow. **At 65–79%**, adjust coverage or routing and recheck. **Below 65%**, drop the incentive design and investigate where PRs wait. Set those thresholds before launch and apply the quality check throughout.

### What could go wrong

- **Rubber-stamping.** A rotating engineer samples five credited reviews each week and checks whether the reviewer engaged with the change and addressed material issues visible in the diff. If two of the last ten sampled reviews fail, the engineering lead pauses the reward. The review coordinator corrects wrong counts and republishes the team total.
- **Easy PRs crowd out hard ones.** Keep the queue oldest-first and assign an explicit owner to complex PRs. A substantive first review can identify a blocker or ask a concrete question. It needn’t approve the change.
- **The numbers feel like surveillance.** Use existing PR records, private confirmations, and team totals. Skip named rankings. Budget 30 minutes for the weekly sample and 15 minutes for corrections and the team update.
