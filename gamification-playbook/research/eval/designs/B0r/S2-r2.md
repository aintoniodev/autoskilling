# One working day for a useful code review

**The deal.** Run a six-week pilot for the 25-engineer team. Aim for **90% of review-ready pull requests to get a useful first response within one working day**. That means feedback the author can act on, not a promise to approve or merge. The engineering manager protects review time from day one. If the team meets the speed and quality targets, everyone gets one protected two-hour block for learning or tooling of their choice, scheduled during work with sprint scope reduced to make room. No points, rankings, individual prizes, or performance-review use.

## How it works

Each week, two engineers rotate as queue owners. They each get two protected 30-minute blocks per working day to review changes in their area, route specialist work, and chase requests nearing their deadline. An available code owner takes specialist reviews; the queue owners remain responsible for getting a response. At six working hours, the queue flags an unanswered request for backup. If demand exceeds capacity, the manager reassigns work or cuts sprint scope. Nobody is expected to review after hours.

## What counts and what people see

- **Start:** When a non-draft pull request enters the team’s review queue. Count eight hours on a published team calendar, excluding evenings, weekends, and team holidays. Reassigning a reviewer or flipping back to draft does not reset the clock. Track time from “ready” to review request separately to catch delays before queue entry.
- **Stop:** When a qualified reviewer posts an approval that says what they checked, an actionable change request, or a specific question that must be answered before review can proceed. An emoji, “looking soon,” or a handoff does not count. Complex changes can get a substantive first pass without lowering the bar for final approval.
- **Measure:** Use one entry per pull request, regardless of how many reviewers are requested. For requests whose deadline has passed, divide timely qualifying responses by all eligible requests. Unanswered overdue requests count as misses. Report genuinely withdrawn changes separately; a pull request merged without a qualifying response is not a withdrawal.
- **Show:** In the existing PR tool, engineers see the owner, working-time age, and deadline for each open request. A weekly team rollup shows the one-day rate as a count and percentage, median first-response time, and open requests older than two working days. No individual statistics.

## How it ends

Before launch, recalculate the last four weeks using the pilot rules. The reported 2.6-day median is context, not a baseline for the one-day hit rate. Each week, an engineer outside the rotation spot-checks ten randomly selected responses, including approvals, against the same usefulness rubric used on a baseline sample.

At week six, award the time block if **at least 90%** of eligible requests in the final three weeks were on time, **at least 90%** of sampled responses were useful, and the sample shows no drop from baseline quality. Publish the counts and the decision. The reward ends either way. Keep the rotation for four more weeks without a reward. If speed and quality hold without regular overtime or spillover, keep the rotation as normal operating practice. If not, fix the bottleneck rather than extending the contest.

## What could go wrong

| Risk | Response |
|---|---|
| Rubber-stamp approvals or token questions | Invalidate nonqualifying responses found in the audit and correct the rate. Repeated misses trigger a review of the process, not pressure to approve faster. |
| Easy changes get picked first; specialist work sits | Work oldest first by default. Check misses by change size and code area; name a backup for recurring specialist queues. |
| Teams hit the first-response target but leave authors stuck later | Track time from first response to approval and the age of re-review requests. When either worsens, fix follow-through before calling the pilot a success. |
| The reward feels like surveillance or extra work | Publish only team totals, keep review time protected even if the target is missed, and ask weekly whether the rotation is displacing planned work. Stop the incentive early if it drives rushed reviews or after-hours work. |
