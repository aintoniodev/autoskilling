# One-working-day review pilot

**Goal:** Give authors a useful first answer on at least 90% of review-ready pull requests within one working day. That is a response commitment, not a merge deadline. The current 2.6-day median is a starting point, not a baseline for the 90% target.

### What is rewarded

Reward the team for making useful reviews reliably available. If the team meets the target in the final two weeks combined and passes the quality and workload checks below, everyone gets one protected half-day for learning or fixing engineering friction of their choice. The manager removes equivalent planned work so the reward does not become overtime. No individual points, rankings, prizes, or use in performance reviews.

Make the target achievable from day one. Each code area has a rotating primary reviewer and a named backup. On-duty reviewers get two protected 30-minute blocks each working day, with sprint capacity reduced accordingly. Take the oldest requests you’re qualified to review first. If a request is halfway to its deadline without a reviewer available, the backup takes it or finds a qualified reviewer. The author doesn’t have to chase.

### How it is measured

Start the clock when a human-authored PR first becomes non-draft in a team-owned repo, even if nobody has been assigned. One working day means eight hours on the published team coverage calendar, excluding evenings, weekends, and team holidays. Reassigning, reopening, or returning a PR to draft does not restart the clock.

A useful answer is an approval that says what was checked, an actionable request for changes, or a specific blocking question the author can act on. “Looking later,” emojis, bot comments, and handoffs do not count. A large PR can get a useful first answer without getting final approval; required approvals and checks stay in place.

Use PR timestamps to calculate **on-time useful first answers ÷ all eligible PRs whose deadline has passed**, grouped by when they became ready. Late and unanswered PRs are misses. Keep closed-without-review PRs in the count unless the author explicitly withdrew the change as obsolete or duplicate; report those exclusions separately. Before launch, recalculate the prior four weeks using the same rules.

### What people see

In the existing PR queue, show the owner, backup, due time, and oldest unanswered requests. Notify only the person who needs to act. Post one weekly team-level update with the hit rate and raw counts, median response time, oldest unanswered PR, and quality and workload findings. Names are for routing work, not scoring people.

### How long it runs and how it ends

Run for six weeks. Each week, two non-authors audit ten randomly selected first responses, or all if fewer, against the rubric above. Sample the baseline the same way. For the reward, at least 90% of audited answers in the final two weeks must be substantive, with no decline versus baseline, no bypassed required checks, and no recurring after-hours review work reported in an anonymous weekly pulse. If volume is too low to judge, report the result as inconclusive rather than a win.

At week six, publish the result and stop the incentive whether or not it pays out. If the pilot meets the target without harming quality or workload, keep the rotation and protected time as normal work. Otherwise, fix the biggest bottleneck before asking for faster reviews again. Check the hit rate four weeks later without a reward.

### What could go wrong

- **Rubber stamps or token questions:** Invalid answers found in audits don’t count. Pause the pilot if speed pressure leads anyone to bypass a required check.
- **Easy PRs get attention while hard ones age:** Use the oldest-first queue and inspect misses by code area and PR size. Cross-train backups where specialist availability is the constraint.
- **The first reply gets faster but the author stays blocked:** Track time to final review disposition and inspect stalled PRs at the weekly check-in.
- **Review work crowds out delivery or moves after hours:** Reduce planned feature work when the rota starts. If the protected blocks routinely aren’t enough, rebalance capacity rather than asking reviewers to catch up at night.
