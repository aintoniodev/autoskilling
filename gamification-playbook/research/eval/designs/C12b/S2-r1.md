# One working day for code review

Run an eight-week pilot for the 25 engineers. The aim is for every author to get a useful first response within one working day. Use the existing review queue and offer each review group one paid hour for an activity they choose if they reach their milestone.

## Make reviews easier to pick up

In week 1, give a few authors and reviewers 30 minutes of protected time to identify what causes waiting. Agree on a staffed review calendar, a rotating primary reviewer and backup for each group, and a protected review slot each working day. Put the oldest ready PRs first in the existing queue. Post the fixes in the team channel and say which problems engineers raised. Give both groups these changes, private feedback, and two weeks to establish a baseline before either group can earn the reward.

## What earns credit

**A ready PR earns one credit when it gets a substantive review within eight staffed hours and the existing PR record shows that the review advanced the work.** That means an approval accepted by the branch’s existing review rule or specific feedback that the author addresses in a follow-up commit or resolves in the PR discussion. Credit can post after that confirmation. The response timestamp determines whether it was on time.

Start the clock when the author marks a PR ready. Pause it outside the agreed staffed hours and while the PR is back in draft at the author’s request. The backup covers absences. Count each PR once. A duplicate comment, a bare acknowledgment, or a self-review earns zero. If a reviewer withdraws an approval because the review was incomplete, remove the credit unless another qualifying response met the original deadline. Work reviewed through the old route earns the same credit if the existing PR record confirms it. A ready PR with no assigned reviewer still counts in the group’s denominator.

## What engineers see and earn

- **Privately**, reviewers see a prompt confirmation when a review qualifies, their share of eligible assigned PRs reviewed on time, and a personal goal set from their own two-week baseline. Start at 10 percentage points above baseline, capped at 100%. Use the team baseline provisionally for engineers with no eligible cases. Exclude cases outside their assigned coverage. Personal goals carry no payout, and each new case is a fresh chance.
- **In the existing team channel**, show each group’s aggregate progress, eligible PR count, milestone, and reward date. The milestone is a 15-point improvement over the group’s baseline share of eligible PRs earning credit, capped at 90%. Each group can earn one paid hour together in its four-week window. Managers see group totals only. Keep individual figures out of performance reviews.

## Timing and decision

Use two existing review groups of roughly equal size and draw which starts first. Both get the queue fixes and feedback in weeks 1–2. The first group can earn the reward in weeks 3–6 and the second in weeks 5–8. Compare each group’s change from baseline in weeks 3–4, when only the first group has the reward. Keep the queue order, rota, and review time in place after rewards end. Check both groups again in weeks 11–12.

Decide using one number: **the percentage of eligible ready PRs that receive a useful first review within one working day**. Calculate it from PR timestamps and check usefulness in the weekly sample, including responses that earned no credit. Keep the defaults if the follow-up reaches 80%. If it improves from baseline but falls short of 80%, change the review workflow where PRs are still waiting. If it returns to baseline or worse, drop the incentive and revisit capacity. Repeat the reward in a future rollout only if the early group improved at least 10 points more than the later group during the staggered start. With two small groups, treat that comparison as directional.

## What could go wrong

Reviewers could rubber-stamp PRs, pick easy work, or move difficult work into draft to stop the clock. The pilot owner checks five PRs a week, including credited reviews, late reviews, and exclusions. Before launch, test the count against a duplicate, a withdrawn approval, and a review through the old route. If two of the latest ten audited credited reviews are superficial or invalid, the engineering lead pauses rewards. The pilot owner corrects disputed counts and checks exclusions. The lead fixes the workflow or counting rule before rewards resume. Budget 45 minutes a week for the sample, corrections, and progress update.
