## One working day for a first code review

Give each ready pull request a substantive first review within one working day. The current median is 2.6 days. Run the programme as a review turnaround pilot and call it that.

### Fix the review queue first

In weeks 1–2, ask a few authors and reviewers where PRs get stuck. Give engineers 30 minutes of protected time to try the revised workflow. Use the code host’s existing owner rules to route ready PRs, put the oldest waiting requests first in the shared queue, and agree on a daily review slot with backup coverage. In the next stand-up, show which reported bottlenecks were fixed. If reviewers still lack time or coverage, delay the reward phase.

### What earns the reward

Each review group earns **one paid afternoon off per engineer**, taken on staggered dates, if at least **80% of its eligible PRs receive a substantive first review within one working day** across its four-week reward window. Confirm during setup that engineers value the afternoon and that coverage is feasible. Name the reward in the launch message, then have the engineering lead announce it in person and thank the group for specific improvements.

A submitted approval counts if the reviewer checked the change and its relevant tests or risks. A change request counts if it identifies a concrete issue or next step. An acknowledgement, emoji, bot review, or self-review earns no credit. One PR can earn credit once.

### How it is measured and what people see

Use the code host’s existing ready-for-review and submitted-review events. Start the clock when a human-authored PR first becomes ready in a participating repository. A working day means eight hours on the owning group’s published working calendar, skipping weekends and team holidays. Assign each PR to its owning group and count it in the window when it became ready. Give the final cohort its full working day before closing the tally.

Before launch, walk through four cases in stand-up. A second review earns no extra credit. A dismissed review loses credit unless another qualifying review arrived before the deadline. Returning a PR to draft and reopening it does not reset the clock. A review done in chat counts only when the reviewer records the substantive response in the PR before the deadline. PRs that miss the deadline stay in the denominator.

Reviewers get a private confirmation through the existing review workflow when a review counts, plus an optional personal goal sized to their expected review load. Someone who expects five reviews might aim to answer four on time. After an absence, the next review is a fresh opportunity. The team sees cumulative progress in its existing channel once a week, including the numerator and denominator. Managers get group totals only, with no individual drill-down or use in performance reviews.

### Quality and failure modes

In the existing engineering sync, the review rotation owner samples five credited reviews each week, or all if fewer than five qualify. Check whether each review merits its approval or gives the author a concrete next step. If **two or more fail in a week**, the engineering lead pauses reward decisions, corrects the tally, and addresses the cause before resuming. Engineers can flag a bad count privately to the rotation owner, who checks the PR and fixes the credit. The lead resolves disputes. Budget under an hour a week for sampling, corrections, and the update.

Rushed approvals are the main quality risk. The sample checks for them directly. Cherry-picking easy PRs leaves older requests visible and counts against the group’s rate. Backup coverage handles absences and deadline spikes. If one group regularly covers another’s queue, treat the reward comparison as directional because the groups share reviewers.

### Timing and ending

Give everyone the workflow fixes and feedback in weeks 1–2. Where two existing review groups have separate queues, start the four-week rewards in weeks 3–6 and 5–8. Use the two-week overlap in calendar time when only the first group has rewards, alongside each group’s own pre-reward rate, to estimate what the incentive added. If everyone shares one queue, use a single four-week window and treat the before-and-after comparison as descriptive.

Keep owner routing, the oldest-first queue, and review coverage in place when prizes end. Four weeks after the final reward window, calculate the same on-time rate over those four prize-free weeks. With the quality gate clear, **80% or higher** means keep the workflow and retire the incentive. **65–79%** means change the workflow around the most common remaining delay. **Below 65%** means drop the incentive and revisit review capacity and ownership.
