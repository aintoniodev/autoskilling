# One-working-day code review pilot

**Give every review-ready pull request a substantive first response within one working day.** Run a 12-week pilot. Each of two groups can earn **one paid hour off per engineer** by answering at least **80%** of its PRs on time during its four-week reward window. Announce the reward at kickoff. If a group earns it, the engineering lead hands it over at the next team meeting, and engineers schedule it around review coverage. Both groups can earn it. Individual volume never determines eligibility.

## Fix the queue first

In weeks 1–2, use part of an existing retrospective to ask engineers who open and review PRs where requests stall. Give everyone paid work time to try the revised flow. Set up a rotating first-response reviewer and a backup in each group, reserve review time during the workday, and put the oldest unanswered PRs first in the queue engineers already use. Tell the team which friction it raised and what changed. Resolve coverage gaps before the reward starts.

## What counts

> A review-ready PR counts once when a qualified teammate submits an approval, requests changes with a concrete reason, or records a specific blocker that the author can act on, within eight hours on the team’s published working calendar.

Use the PR system’s existing ready-for-review and submitted-review timestamps. Exclude weekends, holidays and hours outside the team’s working calendar. Calculate the rate over all eligible PRs whose deadline has passed, including unanswered ones. Use the same definition throughout the pilot and calculate the baseline on it. The reported 2.6-day median provides context, while the on-time percentage determines the outcome.

Before launch, replay a few real cases with the team. A reassignment, a second review or a return to draft leaves the original clock in place. A review withdrawn before the deadline only counts if another qualifying response arrives in time. A linked duplicate is counted once under the original request. Bot replies, self-reviews and “I’ll look later” earn no credit. Engineers flag errors privately to the pilot owner, who corrects the tally from the PR record.

## What people see

Use the existing review notification to confirm the response on the PR. Give engineers a private view of their own open requests and on-time responses, with a simple goal of four on time for every five requests they handle. Engineers with fewer requests see their counts. An absence has no penalty. The backup covers the queue, and returning engineers pick up the next request.

Show each group’s progress toward 80% where it already checks review work. Managers get the overall team rate. Individual counts are visible only to the engineer and are excluded from performance reviews. The pilot uses existing PR records and has no named leaderboard.

## Timing and decision

Use two groups based on existing code ownership where possible, and randomly choose which starts first. Both groups get the queue fixes and feedback in weeks 1–2. Group A’s reward runs in weeks 3–6 and Group B’s in weeks 5–8. Compare weeks 3–4 to see whether the reward appears to add anything after both groups get the fixes. Treat the result as directional given the team’s size and shared reviewers.

Before each reward window closes, make the oldest unanswered review queue and backup routing the default. Rewards end after week 8. Use the **on-time substantive-response rate** in weeks 11–12 to decide what to do. At **80% or higher**, keep the workflow. Above the weeks 1–2 baseline but below 80%, change the coverage or queue setup and recheck. At or below baseline, drop the incentive design and use the next retro to find the remaining bottleneck.

## What could go wrong

- **Rubber-stamp approvals or vague blockers.** Sample five credited responses per week in the existing engineering review. Check whether each approval reflects the change and whether each blocker gives the author a next step. If **two of the latest ten sampled responses fail**, the engineering lead pauses rewards. The pilot owner corrects the affected counts and addresses the cause before rewards resume.
- **Review work crowds out engineering or falls on the same people.** Protect the rota’s review time, rotate it, and route absences to the backup. Use the existing retro to catch recurring overload and adjust coverage.
- **Engineers feel watched or the lift fades.** Keep feedback in the PR workflow and publish only group progress. The post-reward check tests whether the queue and coverage changes are enough on their own.

Assign one pilot owner to publish totals, handle corrections and prepare the five-PR sample in under an hour per week.
