# One working day for a first code review

Give authors a useful first review within one working day. Run the programme through the team’s existing pull request queue and chat channel. The current median is 2.6 days. Before launch, calculate what share of recent PRs actually met the one-day target so the team has a baseline for the measure it will use.

## Fix the queue first

Spend the first two weeks on workflow. Ask a few engineers who regularly author and review PRs where reviews get stuck. Give them paid time to try the fixes. Start with a rotating primary reviewer and backup, a protected review block each working day, and automatic routing when a PR is marked ready. Put the oldest unanswered PRs first in the existing queue. Share one concrete change the team made in response to engineer feedback.

## What earns the reward

Each review group earns a **paid half-day off per person**, scheduled with coverage, if at least **80% of its eligible PRs receive a substantive first review within one working day** across its four-week reward window. Confirm with engineers before launch that they value the half-day and with the engineering lead that everyone can take it. Name the reward and the rule in the launch message. The lead announces the result in the team’s regular meeting and thanks the group for a specific improvement.

Use the existing PR ready and submitted-review events. Count each human-authored PR that requires review once, from its first ready timestamp. One working day means eight hours on the team’s agreed working calendar, excluding weekends and team holidays. The first qualifying response is a submitted approval or requested-changes review with a specific note about the diff, a check performed, or a change needed. An emoji, bot response, or “looking now” leaves the clock running. Reassignments, duplicate reviews, and reopening the same PR leave the original clock intact. A merge without a qualifying review is a miss. A genuinely abandoned PR withdrawn before its deadline can be excluded after the programme owner checks the reason.

Report by the week the deadline falls. Include unanswered PRs as misses once their deadlines pass. Before launch, test the count on a duplicate review, a withdrawn or reopened PR, and a valid review submitted through the team’s usual manual review path.

## What engineers see

The reviewer gets private confirmation through the existing notification channel when a qualifying review lands on time. Each engineer can see their own results and gets a goal sized to their queue. For someone handling one or two reviews that week, the next assigned PR is the goal. For someone handling five, aim for four on time. The team channel shows the group’s weekly on-time percentage and the number of PRs behind it. Managers see group totals only. Individual counts stay out of performance reviews. After leave or a missed week, the next PR is a fresh chance.

## Timing, quality, and the decision

Give both existing review groups the workflow fixes and feedback together. Start the first group’s four-week reward window in week 3 and the second’s in week 5. Assign PRs to their existing owning queue so cross-group help cannot change which group gets credit. Compare the groups in weeks 3 and 4 for an early read on what the reward adds. Treat that comparison as directional because engineers can help across queues.

A rotating engineer who already has repo access samples five credited reviews each week, or all of them if there are fewer. **Two reviews in the sample that fail the substantive-review rule, or one missed issue that triggers a revert or incident, pauses the affected group’s payout.** The engineering lead decides when to resume after the programme owner corrects the count and checks a fresh sample. Engineers can flag a wrong count privately to the programme owner. Watch for rushed approvals, premature withdrawals, and ping-pong assignments. Use the backup reviewer when the queue builds up. Keep the count, sample, and update to under an hour per week for the programme owner.

End prizes after each group’s four-week window. Keep automatic routing, oldest-first ordering, and protected review time in place. Four weeks after the last reward window closes, use the **on-time substantive first-review rate across those four prize-free weeks** to decide. At **80% or above**, keep the workflow and retire the reward. At **65–79%**, adjust routing or review capacity and measure again. Below **65%**, drop the reward programme and revisit what is making reviews wait.
