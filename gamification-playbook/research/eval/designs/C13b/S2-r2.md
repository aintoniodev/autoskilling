## One working day for a review

Run an eight-week pilot for the 25-engineer team. Aim for **85% of eligible pull requests to receive a substantive first review within one working day**. The current median is 2.6 days. Give engineers protected review time and a clear person to hand off to when they’re overloaded.

### What earns the reward

Each of two review groups earns **two hours of paid time off per member** if at least 85% of its eligible PRs receive a qualifying review during its four-week reward window and the quality check passes. Confirm with engineers up front that they value the time off and can realistically take it. Name the reward and threshold in the launch message. When a group earns it, the engineering lead announces it at the next team meeting, thanks the group for a specific improvement, and makes sure the time gets booked.

The rule engineers see is **“A PR counts once when a requested reviewer submits an approval or actionable changes by the end of the next eight working hours.”**

### How it’s measured

Use existing code-host events. The clock starts when a human-authored PR is ready and first assigned to a review group. Use a shared team calendar and published working hours. Reassignment, a push, or closing and reopening the same PR preserves the original clock. Drafts and bot PRs are ineligible. A genuine withdrawal before the deadline can be excluded with a recorded reason. An unanswered PR whose deadline passes counts as a miss. Attribute the PR to the window in which its clock started and let the last deadlines settle before scoring.

The code host records the review decision and its reviewer. Self-reviews, bot reviews, acknowledgments, and empty requests for changes earn no credit. The pilot owner samples five credited reviews per active group each week, or all of them if there are fewer. Check that approvals show evidence of engagement and that requested changes identify something the author can act on. **Two inadequate reviews in a weekly sample pause reward credit for that group.** The engineering lead decides when to resume after the issue is fixed and a fresh sample passes. The pilot owner handles disputed counts privately and corrects them using the existing PR history.

### What engineers see

After a qualifying review, the reviewer gets a private confirmation in the existing review workflow. Each engineer gets a private view of their open review deadlines and a personal goal of answering four out of five requests on time, sized to actual volume and adjusted for coverage. The existing team channel shows weekly group totals and progress toward 85%. Managers get those totals without a per-person drill-down. Keep pilot data out of performance reviews. After leave or a missed week, pick up the next request.

### How it runs and ends

- **Weeks 1–2.** Talk to engineers in both groups about what stalls reviews. Give both groups protected time to try the workflow. Fix the biggest barriers, show what changed, and establish the baseline using the same scoring rule. By the end of week 2, make reviewer routing and backup coverage automatic for ready PRs, with the oldest deadline first in the existing queue.
- **Weeks 3–8.** Group A earns toward the reward in weeks 3–6. Group B earns toward it in weeks 5–8. Both groups get the same workflow and feedback throughout. Use weeks 3–4 to see whether A improves more when the reward starts. Treat that comparison as directional given the small team and shared work.
- **Four weeks after rewards end.** Measure the same one-day review rate with the workflow still in place. At **85% or above**, keep the workflow and retire the reward. At **70–84%**, fix the most common cause of misses and recheck. **Below 70%**, drop the incentive format and revisit review capacity and routing.

### What could go wrong

Fast approvals can hide weak reviews, so the quality threshold can pause credit. Authors could delay requesting review or split PRs to inflate the count. Automatic routing closes the first loophole, and the weekly sample can catch artificial splits. Large PRs and absences can overload the same reviewers, so the rotation needs a named backup and protected review time. Generate totals from existing events and cap the owner’s weekly work at an hour, including sampling and count corrections.
