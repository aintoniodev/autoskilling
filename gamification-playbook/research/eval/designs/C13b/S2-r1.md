# One working day for code review

Run a seven-week trial to give authors a decision on their pull request within one working day. Use the team’s existing review tools and make the incentive a single shared reward.

## Fix the queue first

In week 1, give a few authors and reviewers paid time to identify where reviews stall. Use recent PRs to check for unclear ownership, oversized changes, and competing deadlines. Agree on a primary reviewer and backup for each area, protect a short review block each working day, and put the oldest ready PRs first in the queue engineers already use. Tell the team which fixes came from their feedback. Start the reward only once reviewers have capacity to use the new process.

## Reward and measurement

**Launch rule:** “If at least 85% of your group’s ready PRs receive a substantive human review within one working day in each of two consecutive weeks, the group earns a paid team lunch.” Announce the lunch at launch, schedule it during working hours, and have the engineering lead thank the group in person for a specific improvement.

Calculate the rate from existing PR and review events. Start the clock when a PR is ready and a human reviewer has been requested. Use eight hours on the group’s published working calendar, pausing outside working hours and on holidays. Count the first submitted approval or request for changes that reflects a review of the diff. An actionable request for changes earns the same credit as an approval. Each PR counts once. Group PRs by the week their deadline falls in, including overdue PRs that still have no review.

Before launch, test the rule on a duplicate review submission, an approval dismissed before the deadline, a draft marked ready on Friday, and a PR discussed in chat. Duplicate submissions earn one credit. A dismissed review needs a valid replacement within the original deadline. Friday’s clock carries into the next working day. The chat discussion counts once the reviewer records the decision on the PR. Reassignment or a return to draft after review has started leaves the original deadline in place.

## What engineers see

A submitted review gets a private confirmation showing whether it counted. Each engineer sees their own pending reviews and deadlines. The team sees its weekly rate, the number of PRs behind it, and progress toward the lunch in its existing team channel. Managers receive the same aggregate view. Programme data stays out of performance reviews. A missed deadline leaves the next PR as a fresh chance to contribute.

## Timing and ending

Give everyone the queue fixes and feedback in weeks 1–2. If the team already has two independent review queues, run the reward in weeks 3–5 for one group and weeks 5–7 for the other. Compare their rates in weeks 3–4 for an early signal of what the lunch adds. If the team shares one queue, run one team-wide reward in weeks 3–7 and use weeks 1–2 as the comparison.

By week 7, make reviewer routing and oldest-first triage the defaults. End the reward that week and check the same on-time review rate across weeks 8–11. Calculate a four-week pre-launch baseline using the same rule. Keep the workflow at 85% or higher, adjust it if the rate improves on baseline but falls short of 85%, and drop the trial-specific process if the rate returns to baseline or lower.

## What could go wrong

- **Rushed approvals.** An engineering lead samples five credited reviews each week, or all if fewer than five, against the diff and existing review standards. Pause reward qualification if two are perfunctory or one misses a material defect the review should have caught. The lead decides when the issue is fixed and qualification can resume.
- **Delayed requests or cherry-picking.** Assign reviewers when PRs become ready, use oldest-first triage, and include open misses in the rate. The programme owner spot-checks ready PRs with no reviewer and corrects disputed counts from the PR history.
- **Reviews crowd out delivery.** Protect the review block through sprint planning and route work to the backup during absences. Use existing reports and bring exceptions to an existing team meeting so one owner can run the programme in under an hour a week.
